02 / Why This Stack

Why Astro + Medusa

Why Astro for the storefront

🔍

SEO by default

Every page ships as fully-rendered HTML. No JavaScript has to execute before search engines or link previews see the content — critical for a catalog whose main job is being found.

⚡

Minimal JavaScript

Astro's "islands" model ships plain HTML/CSS unless a component needs interactivity. Visitors download a fraction of a typical React/Vue SPA — faster on mobile networks.

🌐

Static output on a CDN

No server handles visitor traffic for the catalog. Cloudflare's edge serves HTML from the nearest location — faster and free at this project's scale.

🧩

Framework-agnostic when needed

React/Vue/Svelte components can be mixed in only where interactivity is actually required (e.g. a future cart widget) without forcing a heavier rendering model on the whole site.

Why Medusa for the backend

🗂️

Structured commerce data

Variants, calculated pricing, regions, stock levels — a real data model instead of hand-written text fields.

🖥️

Admin dashboard included

Product and category management through a proper UI at /app — no code or git knowledge required to edit the catalog.

🔌

Headless by design

Ships an API, not a rendering engine — the natural fit for a build-time data source feeding a static frontend.

📦

Commerce modules pre-installed

Cart, checkout, payment, orders, promotions, and customer accounts already ship in the core — dormant today, available without a platform change.

03 / Comparison

vs. nopCommerce (ASP.NET MVC)

A useful comparison is against another real commerce platform, not a licensing model. nopCommerce ships a full storefront, admin, and checkout out of the box on ASP.NET MVC. Evaluated against this project's actual scope — a catalog with no online checkout — the two platforms trade off differently:

DimensionnopCommerceAstro + Medusa (current)
Rendering model Server-side render (Razor) on every request Pre-built static HTML served from CDN — no render cost per visit
Page load speed Depends on server + DB round-trip per request Consistently fast — no query happens when a visitor loads the page
Traffic spikes Needs the app server/DB to scale with load CDN absorbs it; backend is barely touched by visitor traffic
Hosting cost .NET app server + SQL Server running continuously Storefront hosting free/static; backend a small Node service, only needed for admin edits and rebuilds
Built-in commerce features Cart, checkout, payments, promotions, multi-language — ready immediately Equivalent modules exist in Medusa's core but are unconfigured — extra wiring required
Deep domain customization Requires learning nopCommerce's plugin architecture Cosmetics-specific logic (JAN codes, license numbers) written directly in project code
Catalog-only

Current scope

Astro + Medusa fits tighter — free static hosting for visitors, a lightweight backend only for admin.

Full store

If scope expands

The comparison narrows — nopCommerce has checkout ready today; Medusa's equivalent modules exist but need wiring.

Either direction, no full rewrite is required from where the project stands today: moving to nopCommerce means discarding the static Astro frontend entirely, while wiring up Medusa's dormant modules builds on what's already deployed.

05 / Ideas Ahead

What's worth building next

Webhook-triggered rebuilds

Medusa calls a Cloudflare Pages deploy hook whenever a product, price, or stock level changes in the Admin — closes the gap between editing data and the static site reflecting it, without a manual redeploy.

Client-side search (Pagefind)

An index built alongside the site, searchable entirely in the visitor's browser — no server, no added hosting cost. search-index.json.ts already produces the data this would consume.

"Call me back" lead capture

A lightweight Cloudflare Worker (or Astro API route) that takes a phone number and forwards it to Zalo/email — captures interest without requiring the visitor to message first.

License number lookup

A page linking each product's cosmetic license number to the Drug Administration's public portal — reinforces the "verifiable origin" positioning already present in the product pages.

Incremental cart, before full checkout

Ship Medusa's Cart API alone (no payment) first — a real "add to cart" experience that still ends in a Zalo handoff with the cart contents pre-filled, as a bridge toward full payment later.

06 / Expansion

Checkout & order management

This is the one expansion path that changes the architecture rather than just adding a page — worth walking through in detail: what breaks, what has to change, and how feasible it actually is given what's already built.

Why this is architecturally different

Everything built so far works because the site is read-only and static — Astro asks Medusa for products once, at build time, and the result doesn't change until the next build. A cart and an order are not catalog data — they're live, per-visitor state that changes by the second (items added, stock reserved, payment confirmed, status updated). A build produces one shared snapshot for every visitor; it cannot represent one specific visitor's cart right now.

Today (catalog only)With real checkout
Astro fetches products from Medusa once, at build time The storefront needs a piece that talks to Medusa live, per visitor — cart, payment, order status
Output is plain static HTML files on a CDN Cart/checkout pages need a running process (an Astro API route/server island, or a small separate app) calling Medusa's Cart and Payment APIs on demand
No order data exists on the storefront side Orders live in Medusa; the storefront shows "your order status" without waiting for a rebuild

How data sync works once checkout is live

Medusa remains the single source of truth throughout — no second database, no custom sync job:

Catalog stays build-time — unchanged

Product listing, category, and detail pages keep working exactly as today: static, fast, free to host. Browsing never needs a live call to Medusa.

Cart/checkout becomes a live island

Only cart and checkout screens run code calling Medusa's Store API directly — cart.create, cart.addLineItem, cart.complete. Astro supports this today via API routes or server islands, without abandoning static output for the rest of the site.

Order status is queried live, not rebuilt

"My order" pages query Medusa's Order API the same way. The Admin dashboard shows the identical order immediately — same database, no duplication.

Catalog freshness after checkout ships

Stock changing from real orders is exactly why the webhook-rebuild idea (section 05) becomes worth adding at this point — keeps the static catalog from drifting from what checkout actually allows a customer to buy.

Feasibility & convenience assessment

Low risk

Foundation already in place

Cart, Payment, and Order modules ship in the currently-installed Medusa core — no new backend platform, no data migration.

Medium effort

New moving part required

A live-calling layer (API routes or server islands) has to be added to Astro — new code, not new infrastructure category.

No rewrite

Catalog pages untouched

Every page built in section 04 keeps working exactly as-is; only cart/checkout/order screens are new.

Bottom line: adding checkout and order management is feasible without discarding anything already built — it's an additive change to the storefront (a live layer for cart/checkout) and a configuration change to the backend (enabling payment providers), not a platform migration. The convenience payoff is that Medusa's Admin dashboard — already in daily use for products — gains order visibility for free, since orders and products live in the same database from day one.
