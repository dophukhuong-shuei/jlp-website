What Medusa is actually doing today

The storefront (storefront/src/lib/medusa.ts) calls exactly three read-only Store API surfaces, all at build time — never from the visitor's browser:

Store API areaStatusHow it's used here
product.list In use Paginated product fetch per category/region, including calculated prices and stock levels.
category.list In use Populates category pages and navigation.
region.list In use Grabs the default region so prices calculate correctly — single-region today.
Pricing engine (calculated_price) In use Real Medusa price calculation, not a hardcoded number — ready for tax/region rules later.
Product metadata In use Escape hatch for JLB-specific fields: JAN code, origin, lot, license number, skin type, sale price.
Cart / Checkout / Payment Installed, unused Ships with core Medusa. Not called — the site links to Zalo/phone instead of checking out online.
Customer accounts / Auth Installed, unused No login, no order history — not needed for a catalog-only site.
Order management Installed, unused Orders are closed manually over Zalo, outside Medusa entirely.
Promotions / rules engine Installed, unused Sale pricing is done manually via metadata instead — simpler for a no-checkout site.
Why this matters: everything in the "installed, unused" rows already ships in the backend's current dependencies (@medusajs/medusa, @medusajs/framework). Turning them on later is a matter of wiring, not a new platform.

Already proven extensible

This isn't theoretical — the backend has a real custom feature built on Medusa's extension points: an admin bulk-import tool (src/api/admin/import-supplier) that reads a supplier's Excel sheet, converts JPY→VND pricing, maps Japanese category names to the shop's own categories, and creates products through Medusa's workflow engine — plus a custom screen bolted onto the Admin dashboard itself for uploading the file. That's Medusa's workflow engine, module system, and Admin UI extension points all exercised in production use already.

Current stack vs. the original static-file plan

The project started as a fully static site: content lived in markdown files, edited through a Keystatic admin panel writing directly to the git repo — a reasonable, genuinely free approach for a small non-commercial catalog. Medusa replaces that content layer while keeping the site just as static to visitors.

Markdown + Keystatic (original)

  • Product edits are git commits — fine solo, awkward for a non-technical shop owner or a second editor
  • No structured product model beyond what's hand-written in frontmatter — no calculated pricing, no stock field with real semantics
  • Bulk import means writing/pasting many files by hand
  • No admin dashboard beyond the CMS form — no reporting, no inventory view
  • Zero path to checkout later without discarding the content layer entirely

Astro + Medusa (current)

  • Real admin dashboard at /app — product, category, and pricing edits with a proper UI, no git needed
  • Structured commerce data model: variants, calculated prices, regions, inventory quantities — not just text fields
  • Bulk supplier import already built, using Medusa's workflow engine — scales past hand-editing
  • Same result for visitors: a fully static site, same hosting cost, same performance
  • Direct, no-rebuild path to checkout, accounts, and orders when the business needs them

The trade-off: Medusa needs a running Node service and a database, where Keystatic needed neither. That cost is paid once, in hosting the backend — it doesn't touch the storefront's static, free-tier deployment on Cloudflare Pages.

What this unlocks later

Because the commerce modules are already part of the installed backend, expanding past a catalog-only site is additive — new wiring, not a new platform.

Real checkout

Register a payment provider module (Stripe, or a Vietnam-relevant gateway like VNPay/MoMo as a custom provider), then switch the storefront from build-time-only reads to using the Cart and Payment Session APIs at runtime. This is the one change that requires a live server instead of pure static hosting.

Order management

Once carts exist, Medusa's Order module gives order history, status tracking, and confirmation emails — visible immediately in the same Admin dashboard already in use.

Customer accounts

The Customer/Auth module is part of the same install — login, saved addresses, and order history for repeat buyers, without adding a new system.

Promotions and rules-based pricing

Today's "sale price" is a manual metadata field. Medusa's promotion engine (already installed, unused) supports discount codes, automatic rules, and bundle pricing when that complexity is actually needed.

Multi-region / multi-currency

The storefront currently assumes one region and VND. Medusa's region/currency/tax modules support more without new packages — the code already calls the region API, it just isn't fed more than one region yet.

Bottom line: the current site pays a small, one-time hosting cost for a Node service and database it barely uses today — in exchange for a real commerce backend that's already been customized once (supplier import) and can absorb checkout, accounts, and promotions later without replacing the storefront or its hosting model.
